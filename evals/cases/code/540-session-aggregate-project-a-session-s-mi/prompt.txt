CURRENT ISSUE #540 — Session aggregate: project a session's microphone, status and start into the session table
## Scope

branch: feat/session-microphone-projection

Applying a command on an existing Session partition that carries microphoneOn, sessionStatus or startedAt leaves the session table untouched: crates/session/aggregates/Session/src/sessions.rs returns early for a session the tables hold (a creation only is projected) and the Session plugin has no hydrate, so fixture sessions have no engine row. live.listSuggestions selects session.status = 'live' and DataCapabilities read the session table, so live.setMicrophone could never make a session live. Add a ProjectPg in the aggregate's own crate that UPDATEs session.status, started_at (stamped once) and microphone_on from the write of an existing session, keyed by the partition Session/<id>, ignoring any other Session row (scene, order, presence, to-create) and tombstones, with its own Postgres tests.

Opened by the harness for #524, whose session stopped on it: #524 waits on this task.

## Business Goal

A live.setMicrophone command applied on a session moves that session's status, started_at and microphone_on in the session table, so the capabilities reading the table see a live session with its microphone on.

## Acceptance Criteria

- given a session 'prep' in the tables and an applied write of Session/<id> with sessionStatus 'live', startedAt and microphoneOn true, when the projection runs, then the session row has status 'live', started_at set and microphone_on true
- given a session already 'live' with started_at stamped, when a later write sets microphoneOn false, then microphone_on is false and started_at is unchanged
- given a write of a scene, a scene order, a presence or a to-create entry on the Session aggregate, when the projection runs, then the session table is unchanged
- given a Session tombstone or a session id the tables do not hold, when the projection runs, then nothing is written and the command is not rejected
- given a write that would leave status 'closed' going back to 'live', when it is applied, then the status-lifecycle invariant rejects it and the table is unchanged
